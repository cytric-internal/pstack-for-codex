### Shipping

**You own what lands. Verify each PR independently, land only the verified run from the root, then keep your hands off the queue.** Use this playbook when the user asks to land or ship a stack, or to enable merge when ready. It begins where `playbooks/babysit.md` ends.

1. **Resolve the forge, then verify every PR independently.** GitHub CLI (`gh`) is the default. If `command -v origin` succeeds and Origin can resolve this repository, use `origin pr ...` for PR view, watch, edit, and merge operations. Otherwise stay on `gh` and record the fallback. Never require Graphite (`gt`). Use one independent verifier per PR, each in its own Codex worktree. Independent verifications can run in parallel when their worktrees are isolated. Exercise the real surface with the relevant installed control skill, such as `control-ui` or `control-cli`, against parent and head. If the needed control surface is unavailable, use the closest real build or test path and report that limitation; fail closed when that surface is required to establish safety. Each verifier returns `PASS`, `PASS+NOTES`, or `FAIL` and posts its verdict on its PR when the user authorized PR updates. The verifier must not have written the code. CI green and an approving bot review are not code verdicts.
2. **Land only the contiguous verified run rooted at the bottom.** Walk up from the lowest unmerged PR and stop at the first one without a passing verdict. Both `PASS` and `PASS+NOTES` pass. A verified PR above an unverified one is not landable. Report the ceiling as a PR number and say what breaks the chain.
3. **Re-check that each verdict still describes the patch.** Record the verdict head SHA, base SHA, and stable `git patch-id` of that PR's base-to-head diff. A rebase or base retarget rewrites SHAs and can silently invalidate a verdict without changing a check. Before landing, compare the recorded patch-id with the current base-to-head patch-id. If the patches differ only in tests, docs, or lint config, rebuild what each lane ran: twice at the verdict SHA and once at the current head. A difference is noise if the two builds at the verdict SHA also show it, or if it is an embedded commit SHA. Judge each difference, not each file, and report each kind of noise with its files. If only noise differs, keep that lane's result, then rerun checks and review the change. Do not reuse a lane result from a dev server or another run with no build output. Rerun that lane. Re-verify other changed patches. When the patch is unchanged, keep the code verdict but rerun mergeability and CI at the current head. Never substitute matching commit messages or an old green check.
4. **Prepare only the bottom PR.** Fetch current trunk. Rebase the lowest verified branch onto the exact trunk tip when needed, push it, and retarget only that PR to trunk with `origin pr edit <pr> --base <trunk>` or `gh pr edit <pr> --base <trunk>`. Repeat step 3 after the push. Do not retarget, arm, or merge descendants yet.
5. **Land one PR at a time.** If the bottom PR is mergeable, squash it with `origin pr merge <pr> --squash` or `gh pr merge <pr> --squash`. If requirements are still running and the user asked for merge when ready, arm only that PR with `origin pr merge <pr> --squash --auto` or `gh pr merge <pr> --squash --auto`. Origin's `--auto` means Origin merge when ready. GitHub's `--auto` means GitHub auto-merge. Wait for the PR to merge before preparing the next one.
6. **Check the active forge's state.** GitHub's `autoMergeRequest` reports only that GitHub auto-merge was requested for one PR. It does not prove Origin merge when ready is armed, a descendant is queued, a patch verdict is current, or the contiguous stack is safe. Confirm the active forge's state for the bottom PR. Report when the forge cannot show that state.
7. **Recompute after every merge.** Fetch trunk and confirm the merged SHA is present. Remove the merged PR from the frozen bottom-to-top list. Inspect the new bottom PR's base, head, checks, and patch-id. A host may retarget a child automatically, but verify it. Repeat steps 3 through 6 for that PR. Ship independent work outside this chain.
8. **Watch the current frontier without changing the queue around it.** On Origin, use `origin pr view <pr> --checks --comments` and `origin pr checks <pr> --watch`, then reread the PR until it reports merged or blocked. On GitHub, use `scripts/watch-pr/watch-pr --queued-stack --stack-prs <bottom>` only to wake the task, then poll `gh pr view <pr> --json state,mergedAt,mergeStateStatus,statusCheckRollup,autoMergeRequest` after each wake. Ignore `READY` until `mergedAt` is non-null or `state` is `MERGED`. Only then run step 7. Treat the PR as failed only when it is closed without merging, a required check fails or is cancelled and blocks a no-longer-pending auto-merge, or merge state is `UNSTABLE` or `DIRTY` with no auto-merge pending. `BLOCKED` while checks are pending or auto-merge is armed is not failure. Do not use Babysit's queued `WAITING`/`merge-queue` stop condition. Use a supported Codex heartbeat only when the user authorized continued monitoring. Do not hold a shell process open with sleep. Report each merge and the new ceiling. If the queue stalls, diagnose before mutating.
9. **Stop at the ceiling.** When the verified run is merged, report what landed, the next unverified PR, and what verifying it would take. Extending the run requires another pass through step 1.

**Reply:** the verified run and its ceiling, each PR's verdict and who produced it, what you armed and how you confirmed it, what landed, and what the next gap needs.
