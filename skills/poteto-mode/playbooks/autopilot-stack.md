### Autopilot-stack

**You own the stack, never the landing. Build and verify the queue with full autonomy, then hand the operator one linear PR chain to review and land.** For "autopilot-stack", "stack them, don't ship", "build the stack, I'll land it". The sibling of **Autopilot-full**. The owner loop and the verification gate are the same; only the terminal differs. There a clean verdict authorizes the owner's merge. Here it appends a link to the one reviewed chain, and nothing auto-ships.

1. **Run the owner loop unchanged.** One isolated Codex worktree agent per PR owns build, registration, self-proof, skeptical Bugbot triage, `$deslop`, `$no-comments`, a first rebase onto current trunk, and babysit to green. The rebase happens before the code-ready report; retain that merge base through fix rounds and rebase again only at merge prep, a `git merge-tree` conflict, or a trunk-caused CI failure. Each owner tracks `decisions.tsv`, `children.tsv` with subagent IDs and expected runtimes, the code-ready SHA, and each later patch-changing push SHA. Owners parallelize only with proven isolation.
2. **Audit on the wake chain.** The operator's explicit go authorizes a thread heartbeat around every 30 minutes. Never hold a shell open to sleep. At each tick, re-read this playbook from trunk and inspect the live goal. Probe owners through supported live status and judge progress by commits, pushes, pull-request or check deltas, and store reports. Cancel or stand down a stuck lane, reconcile partial state, and make at most one bounded replacement. Post a status only for a newly observed tracked change, name only those changes, and end without a message when nothing changed.
3. **Hold the operator gates.** State-then-wait, so a request to state the plan is not a go. On her explicit go, create a goal with the full program objective. The goal continues across turns until the chain is done. On her stop, every owner takes an immediate zero-writes hold.
4. **Verify each round.** Start a verifier swarm at the owner's code-ready head SHA and at each later push that changes the patch. The owner reports STACK-READY with the exact head SHA when its loop is green. The root verifies each round per Autopilot-full step 4, with STACK-READY in place of merge-ready. The root audits receipts in the final report; include two or more focused audit lanes. Nothing enters the stack unverified.
5. **Append on a clean verdict, never ship.** No owner merges, arms auto-merge, or closes. A clean verdict appends the PR to the one linear chain in verified order or an order the operator specified.
6. **Single writer on topology, parallel writers on builds.** GitHub CLI (`gh`) is the default for PR operations. If `origin` is installed and resolves this repository, it may be used instead; record the selected forge. An owner pushes only its own branch after an `ls-remote` lease check and reports its tip and intended parent. The parent alone changes PR bases and chain topology, using `gh pr create/edit` or the corresponding `origin pr` command. Set each child PR's base to its intended parent branch. Never require Graphite (`gt`).
7. **Absorb drift at the root, then re-verify what moved.** The root fetches current trunk and rebases the chain from bottom to top; when conflicts touch an owner's files, that owner fixes its slice. A rebase rewrites SHAs above it. Apply the patch-id rule in `playbooks/shipping.md` at each verdict SHA and rerun mergeability and CI after rewritten pushes. Anything no longer valid goes through step 4 before delivery. The countersign rule is unchanged from Autopilot-full.
8. **Deliver the chain.** Deliver one linear chain of verified PRs, reviewable bottom-up in the selected forge, with each link carrying its verifier verdict in the PR body or a comment. The operator reviews and lands it with their own action.

**Choosing between the autopilots.** Autopilot-full when the PRs are independent and landing authority is granted. Autopilot-stack when the operator wants review before landing, the work is sequenced or coupled, or merge authority is withheld.

**Reply:** links to the stack root and tip, a one-line verdict summary per link, and anything parked or excluded with the reason.
